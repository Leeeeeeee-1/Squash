压缩软件应该具备什么功能

基于 Lee 的四条需求（解压 / 加密码 / 操作简单 / 兼容全部协议）＋ 场景推导，附引擎实测与竞品对照

0 · 结论先行

你的四条需求只覆盖了「合格线」，真正决定一个压缩工具好不好用的，是它有没有解决发送方与接收方之间的落差——格式谁都能解、密码谁都能加，但「发出去对方打不开」「解出来文件名是乱码」「体积太大没法发」这三件事，市面上的工具大多不管。

能形成差异的只有三步

① 中文文件名乱码修复（实测引擎不解决）
② 面向接收方的兼容性预警（该用什么格式发给谁）
③ 镜像与固件直接提取（7-Zip 26 已内建，无人做成 UI）

不要做的事

压缩包内编辑器、密码破解、云盘上传、RAR 创建、格式全家桶 UI。这些是功能蔓延，不是需求。

2 · 功能四层模型

L0 生死线 — 缺了就不是压缩软件

格式识别与解压、压缩创建、拖放、进度、错误提示可读、不损坏文件。Squash v0.1 已全部具备。

L1 高频刚需 — 决定每天用起来爽不爽

功能为什么是刚需Squash 现状
Finder 右键菜单99% 的操作起点在 Finder，不在 App 窗口缺（P0）
Quick Look 预览压缩包不解压就知道里面是什么，省一次解压+删除缺（P1）
默认解压位置正确解到哪、要不要套一层同名文件夹，是最高频的抱怨点已做
记住上次设置每次都重选格式=每天都在重复劳动缺（P0）
中文文件名编码处理国内 Windows 互传必踩，见第 4 节实测缺（P0）
哈希校验确认收到的包没坏、没被改，安全场景刚需缺（P1）

L2 场景加分 — 决定什么时候非它不可

  • 分卷：邮件 25MB 上限、企业微信/微信文件限制，大包必须切开。引擎支持 -v，只是没接 UI。
  • 镜像与固件直接提取：dmg / iso / vmdk / qcow2 / apfs / ntfs / ext4 / squashfs —— 7-Zip 26 已内建（见第 3 节），做成 UI 就是别人没有的东西。
  • 可执行文件结构浏览：MachO / PE / ELF / MSI / NSIS / DMG 都能直接列内部结构，样本初筛不用装逆向工具。
  • 发送前兼容性预警：告诉用户「你选的 AES-256 Zip，对方 Windows 双击打不开，需要 7-Zip」。
  • 自解压包（-sfx）：给完全不懂技术的接收方，双击即解，不用装任何软件。
  • 批处理 / 命令行：把常用组合存成一键动作。

L3 明确不做 — 功能蔓延陷阱

功能为什么不做
压缩包内编辑器（不解压直接改）BetterZip 的护城河，实现成本极高（需完整读写各格式中央目录），你的场景不需要
RAR 创建专有授权，开源工具一律做不到，别承诺
密码破解 / 字典攻击工具定位一旦沾这个，分发和信任都完了
云盘上传、在线分享违背「文件不出本机」的隐私定位
支持全部 200+ 格式的 UI 选择器创建格式越多越难选，7z + Zip + tar.gz 覆盖 99% 场景

3 · 引擎能力盘点（一手实测，非厂商宣传）

直接在 7zz i 上读出来的真实能力边界，这决定了「能做到什么」的上限：

可创建格式7 种：7z · zip · tar · gzip · bzip2 · xz · wim（外加 Hash 校验文件）
可读取格式50+ 种，含分卷 .001、自解压、Office/ePub/JAR/APK
加密编解码器7zAES（AES-256）、AES256CBC（用于 WinZip AES）
压缩过滤器BCJ / BCJ2（x86）、ARM64、RISCV、Delta、LZMA2、PPMd、Deflate64
命令行开关分卷 -v · 自解压 -sfx · 密码 -p · 加密头 -mhe · 字符集 -mcp · 覆盖策略 · 压缩后删源 · 保留权限/符号链接 · 包内过滤 · 增量更新

被严重低估的一点：它不只能开压缩包

同一个引擎能直接展开下列非压缩包结构，全部无需额外工具：

DMGISO / UDFAPFSHFS+ NTFSext2/3/4FATVMDK VHD / VHDXVDIQCOW2SquashFS CramFSMBR / GPTMachOPE (exe/dll/sys) ELFMSI / DOC / XLSNSIS 安装包XAR / pkg CHMRPMDEBUEFI 固件

对安全运营场景（取证、样本初筛、固件比对）这是白送的能力。目前没有任何一个 Mac 压缩软件把这个做成可点的界面——它们只当成「支持格式」写进宣传页。

4 · 实测：三个没人管的真痛点

痛点一：中文文件名乱码（已实测确认）

模拟 Windows 上常见的情形：ZIP 内文件名用 GBK 编码、未设 UTF-8 标志位。用引擎解压的结果：

  • 文件名列表直接变成 뿐...ľ...txt 这类乱码字符
  • 落盘的文件名同样是乱码，内容本身没坏
  • 加 -mcp=936 无效——该参数只管压缩时的代码页，不管解压识别

结论：这不是配置问题，是引擎在 macOS 上不做 GBK 猜测。要修必须自己在应用层做：解压后检测非法 UTF-8 序列 → 按 GBK 重解码 → 重命名。这是国内场景下最高价值的一个功能，也是 Keka / MacPacker / BetterZip 都没有明确解决的问题。

痛点二：加了密的包，对方打不开

三种加密选择，接收方门槛完全不同——大多数工具不给任何提示，发出去才发现对方开不了：

你选的强度Windows 接收方macOS 接收方
7z + AES-256强需装 7-Zip / WinRAR需装 7-Zip 类工具，系统归档打不开
Zip + AES-256强需装 7-Zip / WinRAR，资源管理器打不开同上
Zip + ZipCrypto弱（可被明文攻击）资源管理器原生可开系统归档原生可开

产品化建议：在加密码的同时显示一行「对方需要什么才能打开」，并把强度明显更低的 ZipCrypto 从选项里彻底移除。

痛点三：发出去的文件里全是垃圾

__MACOSX/、.DS_Store、._* 资源分叉文件，Windows 用户打开第一反应是「这什么病毒」。Squash v0.1 已在压缩时默认剔除，这一点比 Keka 默认行为好（Keka 需要手动去设置里勾）。

7 · 定位建议

不要做「又一个压缩软件」。Keka 免费、PeaZip 200+ 格式、BetterZip 功能完备、MacPacker 预览体验极好——在这个赛道里比功能多，赢不了。

真正没人占的位置是：「把东西安全、完整、对方一定能打开地送出去」。围绕这一句，功能取舍立刻清楚：

  • 加密默认用最强的（7z AES-256 + 加密文件名），并主动告知接收方门槛
  • 中文文件名、__MACOSX、路径穿越这些「发出去才发现的坑」全部提前处理掉
  • 大文件自动建议分卷，而不是让用户自己算 25MB 该切几份
  • 附带哈希，让接收方能自证文件没被改动
  • 顺手把镜像/固件提取做出来——安全场景的免费增值点

按这个定位，Squash 不需要跟 Keka 比格式数量，也不需要跟 BetterZip 比编辑能力。它只需要在「交付」这一个动作上做到没有对手。
